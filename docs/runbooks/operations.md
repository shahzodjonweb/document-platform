# Operations runbook

## Startup and contracts

Use the README's two-terminal local startup. API owns business state. Customer app proxies `/api` to its configured backend. Customer files are never served by the static server; API download endpoints re-check ownership, state and expiry. All staff code stays here.

Set `DEBUG=0`, a cryptographically strong unique `SECRET_KEY`, explicit hosts and trusted HTTPS origins in a deployed environment. Set a separately managed `FILE_SECRET_KEY` for encrypted one-use PDF passwords. The same key encrypts every AI document's draft, and a draft a file was made from is kept until the customer deletes it (`apps/studio/keeping.py`). So rotating `FILE_SECRET_KEY` (or `SECRET_KEY` while `FILE_SECRET_KEY` is unset, as the key is then derived from it) makes every kept draft unreadable at once: ✏️ Make changes and the deck editor then fail for every older document, in the chat and on the web, with no way back short of restoring the old key. Rotate it only when that loss is accepted. Keep development sign-in, beta tooling and synchronous execution disabled until a reviewed environment-specific flag policy is installed. Production feature gates intentionally cannot be enabled by setting a client variable.

Schema version is public API `1.0.0`, OpenAPI `3.1.0`, policy `draft-staging-v1`, metric definitions `1.0.0`. Files `contracts/public.openapi.json` and `.sha256` are versioned; generated public types belong only in `document-web`. Customer updates must remain compatible with the deployed backend. Every schema change needs regenerated artifacts and client verification.

## Migrations and rollback

1. Back up the database and current configuration; verify restoration in staging.
2. Apply additive migrations (`manage.py migrate`).
3. Deploy compatible backend/worker images with feature gates closed.
4. Deploy the pinned customer application.
5. Run authenticated upload→quote→reserve→process→download smoke tests, ownership tests, ledger reconciliation and retention checks.
6. Enable only release-reviewed capabilities. Never equate a passing local fixture with production approval.

Rollback closes flags and restores prior application images. Do not destroy usage, payment, audit or task history to undo a deployment. Destructive schema rollbacks require an explicit recovery plan. Reconcile deletion tombstones before making any restored binary available; restoring a backup must not revive deleted private documents.

## Retention and workers

Default retention is 24 hours. Run `manage.py cleanupfiles` every five minutes. It revokes expired assets, deletes private files and password secrets, and sweeps old unregistered binaries. `scripts/cleanup_loop.py` runs `clearsessions` after it, which removes expired sessions. A stale lease is terminally released only when the maximum parser timeout guarantees it cannot still commit output. Current task status and artifact authorization checks prevent a stale worker from charging twice.

The production cleanup daemon has a 384 MiB memory ceiling, including Telegram challenge housekeeping. A running container alone is insufficient: CI and live service verification require a full `Deleted N expired files.` cycle without a restart or OOM kill. The scoped `stabilize-cleanup` server operation can raise only this daemon's previous 192 MiB ceiling in place on the authorized 8 GB server; it never restarts containers or updates another service.

`manage.py runworker` drains the durable database outbox. Use `--once` for a bounded operational pass. Do not combine the direct worker with the Celery dispatcher unless reviewing the at-least-once execution model. Duplicate attempts are safe at application claim/settlement boundaries, but production process death and PostgreSQL contention need the documented load gate.

API metadata logs contain correlation IDs and stable errors. General logs and analytics must not contain document contents, filenames, user answers/prompts, passwords, raw session tokens or presigned links. Stored support messages are owner support data, not analytics.

## Staff access

`manage.py setup_staff USER --role ROLE` prompts for credentials and provisions TOTP. Supported roles: Analyst, Support, Operations, Finance, Content manager, Administrator. Reset MFA only via authorized local administration with `--reset-mfa`; it revokes existing staff sessions. Staff login is throttled. TOTP codes are single-use per accepted counter. Ops has an eight-hour opaque, hashed session cookie scoped to `/ops/`, independent of the customer realm.

Analyst sees aggregate reports and anonymized feature CSV. Support can inspect customer/task metadata and resolve cases with reasons. Finance sees currently gated financial views. Operations sees task/system diagnostics. Content manager sees plan/localization status. Administrator may use all implemented operations. There is no staff file-content download endpoint or general impersonation action. Privileged account metadata views and exports are audited.

An account deletion that support handles (a customer who asks for it by message: neither the web nor the bot has a delete button yet) must run Admin → Users → the account → AI documents kept for changes → Delete AI documents (Support, Operations or Administrator; audited as `account.documents_delete`). Nothing else removes the drafts kept for ✏️ Make changes and the files they hold, which never expire on their own: only an account deleted through `DELETE /me` (which sets `deletion_requested_at`; no screen calls it yet) has them deleted by the cleanup, on every pass (`apps/studio/keeping.py` `delete_leaving`).

## Metrics and finance

Acquisition: distinct canonical accounts created in `[date_from,date_to)` after converting selected local midnights to UTC. Channel means first verified channel for acquisition, task origin for job metrics. Production excludes `is_test` accounts. Daily chart, summary and CSV use the same filters. Current plan, payment history and current paid entitlement must never be conflated.

Job success: succeeded atomic tasks / (succeeded + failed tasks) in the accepted-task cohort. No-op and canceled tasks are excluded. Seven-day activation includes only mature signup cohorts; missing denominators display unavailable, not zero percent. Charts provide equivalent tables.

Billing is in so'm, two ways: a card transfer reviewed by hand (the card and prices are saved in the admin panel, and a plan starts only when Finance approves the receipt), and automatic payment through inPAY, with one inPAY kassa for the bot and one for the website (each kassa's key is saved on its own card in Administrator → Integrations; a plan starts only when inPAY itself confirms the payment, see apps/commerce/README.md). In each place customers get one way at a time: that place's kassa while it is set up and working, card transfer otherwise, including for 10 minutes after that kassa fails to open a payment; the kassa cards and the card-transfer card in Administrator → Integrations say which it is now in the bot and on the website. If inPAY payments stop arriving, read the Telegram alerts first ("inPAY could not open a payment in the bot / on the website" names inPAY's reason), then press Test connection on that kassa's card; unticking the box there stops new payments through that kassa at once and brings card transfer back there. In the bot, customers can also save a card and renew monthly through inPAY Avto PAY (key and switch on the bot kassa's card; "Only me" until it has been tried with a real payment); renewals are charged by `cleanupfiles` on the period's last day and retried a day and three days later. If renewals stop arriving, read the "inPAY refused to charge a saved card" alerts and press Test Avto PAY; unticking saved cards there pauses every renewal without touching the cards. Never create a payment or a paid user from a UI success event or from the account's plan field alone; a staff-assigned plan is a separate, audited action. Financial pages report so'm collected and refunded, paying accounts and the review queue.

## Before public release

- Validate the live bot/browser/Mini App canonical account on Telegram iOS, Android and Web, including browser challenge confirmation, CSRF, launch freshness/replay handling and cookie fallback behavior.
- Run PostgreSQL concurrent reservation/duplicate delivery tests, backup/restore and deletion reconciliation.
- Install stable reviewed engines and isolate parsers in a non-root Linux sandbox with network disabled, readonly runtime, memory/CPU/process/temp-disk limits. Local subprocess limits are not full exploit containment.
- Test worker termination/reaper, sandbox file limits, queue fairness and actual transport limits. Observe worker heartbeats; queue depth is not proof of healthy workers.
- Configure reverse proxy TLS, request size limits, shared distributed rate limiting, private storage, monitoring and scheduled retention. Restrict built-in data-maintenance admin separately.
- Complete translated-copy, privacy/support contact, commercial price and provider/license reviews. Keep later release gates closed until their original backlog acceptance evidence exists.

The supplied Compose file is a local integration scaffold with pinned public image digests. It was not run because Docker is absent on this host. Its development switches and shared parser host must not be presented as a completed production deployment.

## Admin-managed integrations and extended workers

Administrators configure Telegram token/username/web application URL and AI text/image models in `/ops/integrations`. Secrets are never redisplayed. The same Document generation card tunes the calls: a reasoning effort for writing calls (the model's own by default) and for the photo choice (`low` by default), a processing tier (`priority` is faster and dearer), and "Write long new documents in parts side by side" (off by default). With that switch on, a new deck or document of 8 sections or more is planned in one short call (stage `plan` on the AI usage page: headings, a deck's layouts and photo subjects, a document's one-line notes) and then written in parts of about 5 slides or 3 pages, all at once; a deck's photos are fetched from the plan meanwhile. A plan that fails leaves the job written one part after another, as before. Check the first planned decks and documents in `/ops/generations` before leaving it on. Local Start/Stop controls are permitted only in the explicit loopback development realm. A production service manager runs `manage.py runbot` with the same database and encryption configuration; the runner reads the encrypted token from the database.

Preserve `.private/integration.key` with the local database backup. In deployment, supply `INTEGRATION_ENCRYPTION_KEY` through managed secrets and test a restore before rotating it. Studio drafts and saved education content also use this cipher. Losing the key makes encrypted content unreadable.

Use `runworker` for ordinary jobs and a separate `runbatches` process for long batch parents. `runworker --lane ai` (the `ai-worker` service) takes AI decks, documents and CVs only, beside the worker, which still takes every job: two AI jobs then run at once, a burst of decks no longer queues behind one at a time, and with the lane down the worker alone runs everything. Both claim a job through its row lock, so a job runs once. Queuing a job and settling a bot job push a token onto a Redis list (`apps/core/wakeups.py`) that the runners and the bot's delivery loop block on, so work is picked up at once instead of at the next look (every 1 s for the worker, 2 s for the bot); without Redis, or with it down, they look on that timer as before. This prevents a batch of 25 documents from blocking all ordinary work. A third, `runreader` (the `reader` service), reads the files CVs are made from: never the API or the bot. Reads queue in `CvSourceRead`, the accounts taking turns; a read whose reader died is retried after its lease (three attempts), and SIGTERM finishes the file in hand. A CV draft whose files are still queued is refused with `cv_reading` (409) and the customer waits: in the bot one message says how many reads are ahead and becomes the review (chat state `cv_wait`, looked at every 2 s by `runbot`); when its place has not moved for ten minutes it says reading takes longer than usual, and still becomes the review by itself once read (looked at every 30 s; Check now looks at once). A moment Telegram cannot be reached only delays the next look. A reader that is down shows as reads that stay `queued`, and the web is then told no time (`estimated_seconds` null). `dispatchoutbox` is the alternate Celery publisher; do not run competing queue modes without a deliberate deployment topology. A published event remains undelivered until terminal settlement. Polling drains bot delivery retries, the CV waits and posts; a webhook deployment requires `dispatchtelegram` (which also looks at the CV waits once a run) and `deliverbot` workers. Posts (Admin → Posts, Administrators only) go out from `runbot` one at a time, at most 20 messages a second (under Telegram's 30 for a bot, which customers' replies share; Telegram's answer time makes it slower in practice); a slow-down request from Telegram pauses the post, not the bot, and so does Telegram being unreachable or the post's image not being readable (the post tries again every 30 seconds; only the copy at the head of the line spends attempts). A copy cut off between the send and its result (a lost lease, or a connection that broke or went quiet after the request went out) is marked `failed/interrupted` and not sent again, while a connection that never opened (refused, DNS, TLS, the 10-second connect bound) only pauses the post; a tap on its button counts it as delivered and stops any further send. A chat Telegram refuses fails at once (`telegram_rejected`); someone who asks to be deleted while a post is sending is skipped. In webhook mode each `deliverbot` run sends posts for up to 50 seconds, so schedule it every minute while a post is sending. Test accounts get posts only through the local simulator. Configure recurring `cleanupfiles` and `reconcilepayments` (it expires lapsed periods and counts invitations) explicitly in the deployment scheduler. `cleanupfiles` (the `cleanup` service, every five minutes) also counts invitations and gives the Plus months they earn, so rewards do not wait for `reconcilepayments`.

Local authoring is available only in DEBUG. Production must select a configured AI provider or disabled mode. Card payments need the card, and inPAY payments an inPAY key, with the prices saved in the admin panel; nothing is on sale until they are. Sandbox test accounts and facts are excluded from production grants and reports even if copied from a development database.

## The new editors' switches

`/ops/editor` (Operations) holds the switches `editor_v2`, `pdfcraft`, `text_edit`, `deck_editor`, `edit_buttons`, `count_once`, `photos_task`, `vector_blackout`, all off by default, and the free-work budgets per account per day. A change takes effect at once and is audited. To go back to the old editor: admin → Editor → `editor_v2` off. Until the first save there, `EDITOR_FLAG_<NAME>=1` and `EDITOR_BUDGET_<NAME>=<seconds>` in the environment answer instead. The web reads the switches from `/studio/config`, `limits.editor`.

## The AI categories' switch

`/ops/categories` (Operations) holds one switch for the AI PDF and AI Slides categories and one tick per category, off and empty by default. It is the `IntegrationConfig` row `categories`, `{on, live}` (`operations/categories_settings.py`); there is no environment fallback, and it is not an editor flag, so the web is not told. A change takes effect at once and is audited (`categories.settings`, before and after). Only a `ready` entry of the catalogue (`apps/studio/categories/data`) can be ticked: a draft is shown greyed with its renderer (a deck, or its PDF templates) and the checks a person makes before it is ready. A category shows in the bot when the switch is on and it is ticked; Other (Boshqa) is always beside it. Off, and for every flow without a category, AI PDF and AI Slides are today's. An entry a later deploy sends back to draft leaves the bot by itself; its tick stays in the row until the next save on the page, which drops it, since a draft cannot be ticked.

Deploy and rollback rules (there are no migrations):
- Every push to `main` deploys, so the switch and its ticks normally stay as they are through a deploy. API and bot swap before the workers, so for up to ten minutes an old worker may run a job made by new code; that matters only when the old workers lack something the new code serves:
  - The first deploy of categories: keep the switch off until its last runner has rolled. Workers from before categories would write a category draft as plain sections.
  - A deploy that adds an entry, a renderer (the PDF templates' first), or a template a ticked entry now uses: leave a new entry unticked, and untick an entry whose template is new, until the deploy's last runner has rolled. A worker that lacks a template draws the fallback (`template_fallback` on the artifact); one without the PDF renderer fails a PDF category job with `category_unavailable`.
  - Anything else (copy, prompts, fixes, a catalogue edit as below): ticks stay on through the deploy.
- A catalogue edit of a live entry is safe: ids are append-only, so an old worker finds every part and draws a valid document with its own copy.
- An id a worker does not know (a catalogue rolled back) fails the job with `category_unknown` before any provider call; failed jobs are not counted. A PDF category draft reaching a worker that only draws decks fails with `category_unavailable`, also before the provider and not counted.
- Turning the switch off mid-flow: the bot builds without the category from then on; category drafts already made still quote and generate.
- Rolling back to code from before categories: turn the switch off, wait out the 24-hour draft lifetime, then roll back. Old code would write a category draft as plain sections.
- Logs carry category, field and block ids, codes and counts only, never a fact value, a description or a file's text.

## Rate limits and Redis

`throttle` and `account_limit` (`apps/core/views.py`) count per account on the `limits` cache, Redis when `REDIS_URL` is set, so every gunicorn process sees one counter. With Redis away, each call is counted in `AuthRateLimit` rows instead and `Limiter store unavailable` is logged; nothing else depends on it, as every other cache stays in the process.
